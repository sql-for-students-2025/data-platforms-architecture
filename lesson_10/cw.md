### Подмена таблиц и партиций в Clickhouse

---

В связи со спецификой работы **Clickhouse** использование ReplacingMergeTree не всегда оправдано, так как запросы с использование FINAL заставляют систему немедленно применить изменения, что на большом количестве данных может сильно усложнить работу Clickhouse вплоть до остановки системы. Поэтому для таблиц, исользующих full load (чаще всего - справочников) можно использовать функционал подмены таблицы. Подмена таблицы является атомарной операцией (выполняется полностью или не выполняется совсем) и выполняется немедленно, в отличие от "схлопывания" дубликатов в ReplacingMergeTree, которые выполняются в любое время, когда системе это будет удобно (т.е нет гарантии, что это произойдет сразу). 

Рассмотрим на примере:

``` sql

--создаем две таблицы, специально делаем их разными, чтоб показать, что подмена таблицы может осуществляться для любых двух таблиц
--все это вы можете провернуть в своей бд

create table change_test_1 (
	id Int16
)
engine=MergeTree
order by id;

create table change_test_2 (
	id Int16,
	str_name String
)
engine=MergeTree
order by id;

--проверяем, что таблицы создались и в них нужные нам столбцы
select * from change_test_1;
select * from change_test_2;

--вставляем значения, чтоб наглядно увидеть результат подмены таблиц
insert into change_test_1 values (1);
insert into change_test_2 values (1, 'first')

--осуществляем подмену
exchange tables change_test_1 and change_test_2;

--проверяем, что таблицы поменялись местами
select * from change_test_1;
select * from change_test_2;
```

Аналогично можно делать и с партициями. Например таблица фактов, как правило, имеет очень большой объем и часто имеет партиционирование по одному из полей (чаще всего по дате). 
Делать полную загрузку таблицы и подмену очень дорого и долго. В случае с *incremental load*, например, раз в сутки, заливаются данные за прошедший день + лаг за прошедшую неделю. Тогда получается, что у нас один день с абсолютно новыми данными и еще 7 дней данных, которые при обычной вставке могут задублироваться. В таком случае мы можем осуществить подмену **партиции** для имеющихся данных. 
Рассмотрим на примере:
В ночь с 2026-11-10 на 2026-11-11 загружаются данные по транзакциям, которые произошли 2026-11-10, а так же обновляются данные по транзакциям с 2026-11-03 по 2026-11-09. 
В случае с транзакциями за 2026-11-10 мы можем не переживать, так как их еще нет в нашей системе, но данные по транзакциям с 2026-11-03 по 2026-11-09 уже есть и необходимо их заменить на новые данные. Тогда, для периода с 2026-11-03 по 2026-11-09 мы делаем **подмену партиции** (по сути - удаляем старые данные и вставляем на их место новые). Операция, так же как и подмена таблицы, является атомарной и выполняется немедленно.

На практике это выглядит следующим образом:

```sql

--для начала создадим таблицы с партиционированием по полю с датой, чтоб наглядно показать как это работает
create table change_test_3 (
	id Int16,
	str_name String,
	dt Date
)
engine=MergeTree
order by id
partition by dt;

create table change_test_3_stage (
	id Int16,
	str_name String,
	dt Date
)
engine=MergeTree
order by id
partition by dt;

--заполним данными таблицы
insert into change_test_3 values (1, 'first', '2026-10-10');
insert into change_test_3 values (2, 'second', '2026-10-11');

insert into change_test_3_stage values (3, 'first', '2026-10-10')
insert into change_test_3_stage values (4, 'second', '2026-10-11')

--проверяем, что строки вставились
select * from change_test_3;
select * from change_test_3_stage;

--осуществляем подмену партиции. Имя партиции будет равно дате, которой принадлежит строка. в нашем случае '2026-10-10'
alter table change_test_3 replace partition '2026-10-10' from change_test_3_stage;

--проверяем, что партиция подменилась
select * from change_test_3;
```
