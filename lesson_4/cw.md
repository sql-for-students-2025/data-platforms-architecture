# Занятие 4. Карта источников данных предприятия

### Главная задача занятия

Ответить на вопрос:

> **«Откуда в компании берутся данные, что именно там находится и каким способом эти данные должны попадать на платформу?»**

Научиться строить **Source Map** предприятия и определять для каждого источника:

* владельца;
* бизнес-домен;
* тип данных;
* способ получения;
* частоту обновления;
* объём;
* требования к свежести;
* потенциальные проблемы интеграции.

---

# 1. Разогрев

Вернуться к домашнему заданию прошлого занятия.

Показать:

```text
                    RETAIL
                      │
       ┌──────────────┼──────────────┐
       ▼              ▼              ▼
      POS             ERP            WMS
       │              │              │
       ▼              ▼              ▼
     Sales          Product         Stock
```

Задать вопрос:

> **Если завтра нам понадобится построить витрину продаж, достаточно ли знать названия этих систем?**

Нет.

Нужно знать:

* какие таблицы/сущности там есть;
* кто ими владеет;
* как получить данные;
* насколько они актуальны;
* какие ограничения есть у источника.

---

# 2. Что такое Source Map 

Дать определение:

> **Source Map — описание источников данных предприятия, их содержимого, владельцев, способов интеграции и характеристик данных.**

Простейший вариант:

```text
Source
   │
   ├── Domain
   ├── Owner
   ├── Entities
   ├── Data type
   ├── Volume
   ├── Frequency
   ├── Freshness
   └── Integration method
```

Например:

| Источник   | Домен     | Данные          | Тип                | Обновление |
| ---------- | --------- | --------------- | ------------------ | ---------- |
| POS        | Sales     | чеки, позиции   | transaction        | минуты     |
| ERP        | Product   | товары, цены    | master             | часы/дни   |
| WMS        | Warehouse | остатки         | operational        | минуты     |
| Loyalty    | Customer  | клиенты, бонусы | master/transaction | минуты     |
| E-commerce | Sales     | заказы          | transaction/event  | секунды    |

# 4. Самое важное — источник ≠ база данных 

Студент должен научиться мыслить **бизнес-системами**, а не таблицами.

Например:

```text
ERP
 │
 ├── product
 ├── supplier
 ├── price
 ├── purchase_order
 └── warehouse
```

Для архитектуры важно сначала:

> **ERP — система управления предприятием.**

А уже потом:

> какие конкретно таблицы мы из неё забираем.

---

# 5. Как выбирать способ интеграции 

Это центральная часть занятия.

Для каждого источника есть несколько вариантов.

## Вариант 1. Full load

```text
Source
  │
  ▼
SELECT *
  │
  ▼
Data Platform
```

Каждый запуск забираем всё.

Плюсы:

* просто;
* легко реализовать.

Минусы:

* дорого;
* медленно;
* большая нагрузка на источник.

---

## Вариант 2. Incremental load

Забираем только изменения:

```text
Source
 │
 │ WHERE updated_at > last_timestamp
 ▼
New / changed rows
 │
 ▼
Data Platform
```

Например:

```text
10:00 → забрали до 10:00
11:00 → забрали 10:00–11:00
```

---

## Вариант 3. CDC

**Change Data Capture** — отслеживаем изменения в базе.

```text
PostgreSQL
     │
     ▼
  Changes
     │
     ▼
   CDC
     │
     ▼
Data Platform
```

Например:

```text
INSERT order 123
UPDATE order 123
UPDATE order 123
```

Каждое изменение может быть доставлено дальше.

---

## Вариант 4. API

```text
Source API
    │
    ▼
GET /orders
    │
    ▼
Airflow / Python
    │
    ▼
S3
```

Проблема:

> API может иметь rate limits, pagination, timeout и ограничения по историческим данным.

---

## Вариант 5. Events / Streaming

```text
Source
   │
   ▼
Event
   │
   ▼
RabbitMQ
   │
   ▼
Consumer
```

Используем, когда важна низкая latency.

---

# 6. Как выбрать способ загрузки 

Дать студентам простую матрицу.

| Требование                 | Подход                  |
| -------------------------- | ----------------------- |
| 1 раз в сутки              | Batch                   |
| Каждый час                 | Incremental batch       |
| Каждые 5 минут             | Micro-batch / streaming |
| Секунды                    | Streaming               |
| Есть `updated_at`          | Incremental             |
| Нужны все изменения        | CDC                     |
| Есть только REST API       | API ingestion           |
| Большой исторический объём | Bulk + incremental      |

Но обязательно сказать:

> Это **не правила**, а отправная точка. Реальное решение зависит от ограничений источника.

# 7. Архитектурные проблемы источников 

Теперь самое полезное.

## Нагрузка на source system

Нельзя просто делать:

```sql
SELECT * FROM orders;
```

каждые 5 минут из production PostgreSQL.

Можно получить:

```text
Analytics
    │
    ▼
PostgreSQL
    │
    ├── OLTP queries
    └── extraction query
             │
             ▼
         performance ↓
```

Поэтому часто используют:

* replica;
* CDC;
* специальные extraction tables;
* incremental extraction.

---

## Schema changes

Сегодня:

```text
orders
----------------
id
customer_id
amount
```

Завтра:

```text
orders
----------------
id
customer_id
amount
currency
```

Pipeline должен пережить изменение schema.

---

## Deletes

Очень важный вопрос.

Что произошло с:

```text
order_id = 123
```

если строку удалили?

Incremental extraction через:

```sql
WHERE updated_at > ...
```

может вообще не увидеть DELETE.

Отсюда:

> **Удаления — одна из типичных проблем построения ingestion.**

---

## Дубли

Например:

```text
order 123
order 123
order 123
```

Нужно определить:

* как идентифицировать событие;
* как дедуплицировать;
* что считать источником истины.

---

# 8. Source of Truth 

Очень важное понятие.

Допустим, цена товара есть:

```text
ERP        → 100 ₽
E-commerce → 105 ₽
Cache      → 100 ₽
```

Какая правильная?

Нужно определить:

> **System of Record / Source of Truth.**

Например:

```text
Product master → ERP
Stock          → WMS
Order          → E-commerce / ERP
Customer       → Loyalty
```

Но иногда один бизнес-объект распределён между несколькими системами.

И это уже архитектурная проблема.

---

### Главная мысль занятия

> **Построение Data Platform начинается с инвентаризации источников. Для каждого источника нужно понимать не только «какие данные там есть», но и кто ими владеет, насколько они свежие, как они изменяются и каким способом их безопасно и эффективно извлекать.**
