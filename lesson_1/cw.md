# 1. Вводная часть

> **Представьте крупный ритейл. Каждый день 1 млн покупок. Бизнес хочет видеть продажи по магазинам почти в реальном времени и строить прогнозы на основе истории за 5 лет. Где и как будут храниться эти данные?**

Показать условную картину:

```text
                 РИТЕЙЛ

Кассы ──────────────┐
                    │
E-commerce ─────────┤
                    │
Мобильное приложение┤
                    │
WMS ────────────────┤
                    │
ERP ────────────────┤
                    │
Loyalty ────────────┘
```

Спросить студентов:

1. Где сейчас находятся данные?
2. Можно ли всё хранить в одной PostgreSQL?
3. Кто должен получать доступ к данным?
4. Как получить отчёт за 5 лет?
5. Как показать покупку через 2 секунды после её совершения?

**Главная мысль занятия:**

> Архитектура данных появляется не потому, что существуют разные технологии. Она появляется потому, что **разные задачи предъявляют разные требования к данным**.

# 2. OLTP vs OLAP — 20 минут

## OLTP

**Online Transaction Processing**

Система предназначена для выполнения большого количества небольших транзакций.

Пример:

```text
Покупатель покупает товар

INSERT order
INSERT order_item
UPDATE stock
UPDATE loyalty_balance
```

Характеристики:

* много небольших операций;
* высокая конкуренция;
* ACID;
* нормализованные таблицы;
* быстрые INSERT/UPDATE;
* текущие данные.

PostgreSQL здесь подходит отлично.

### Пример модели

```text
orders
--------
id
customer_id
store_id
created_at
status

order_items
-----------
id
order_id
product_id
quantity
price
```

---

## OLAP

**Online Analytical Processing**

Задача — анализировать большие объёмы данных.

Например:

```sql
SELECT
    store_id,
    date,
    sum(amount)
FROM sales
GROUP BY store_id, date;
```

Характеристики:

* большие объёмы чтения;
* агрегации;
* сканирование миллионов/миллиардов строк;
* аналитические запросы;
* исторические данные;
* часто column-oriented storage.

Здесь появляется ClickHouse.

---

## Главное сравнение

|          | OLTP            | OLAP                |
| -------- | --------------- | ------------------- |
| Задача   | Транзакции      | Аналитика           |
| Пример   | Оформить заказ  | Продажи по регионам |
| Операции | INSERT/UPDATE   | SELECT/aggregation  |
| Данные   | Текущие         | Исторические        |
| Модель   | Нормализованная | Аналитическая       |
| Пример   | PostgreSQL      | ClickHouse          |

### Важный вывод

Не стоит говорить:

> «ClickHouse быстрее PostgreSQL».

Корректнее:

> **ClickHouse оптимизирован под другой класс нагрузок.**

# 3. Почему появляется DWH

Постепенно возникает проблема:

```text
ERP ────────┐
POS ────────┤
E-com ──────┤
WMS ────────┤──► ?
Loyalty ────┘
```

Данные:

* находятся в разных системах;
* имеют разные форматы;
* разные идентификаторы;
* разное качество;
* разные владельцы.

Появляется **Data Warehouse**.

```text
Sources
   │
   ▼
ETL
   │
   ▼
DWH
   │
   ├──► Reports
   ├──► BI
   └──► Analytics
```

### Идея DWH

DWH — это не просто «большая база».

Это **централизованное аналитическое хранилище с согласованными данными**.

Ключевое понятие:

> **Единая версия правды — Single Source of Truth.**

---

# 4. Почему появляется Data Lake — 10 минут

Затем возникает другая проблема.

Компания хочет хранить:

* CSV;
* JSON;
* логи;
* события;
* изображения;
* сырые данные;
* данные IoT;
* исторические snapshots.

Не всё удобно складывать непосредственно в DWH.

Появляется **Data Lake**.

```text
              Data Lake
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      CSV      JSON     Parquet
      logs     events   files
```

Главная идея:

> **Храним данные в исходном или близком к исходному виде и обрабатываем их позже.**

### DWH

```text
сначала моделируем
        ↓
потом храним
```

### Data Lake

```text
сначала сохраняем
        ↓
потом преобразуем
```

# 5. Lakehouse

Проблема:

DWH хорош для аналитики, Lake хорош для хранения разнообразных данных.

Lakehouse пытается объединить преимущества:

```text
             Lakehouse

       Object Storage
              │
       ┌──────┴──────┐
       │             │
   Raw data     Structured
                   data
       │             │
       └──────┬──────┘
              ▼
          Analytics
```

Идея:

> **Дешёвое и универсальное storage + возможности аналитической платформы.**

Здесь достаточно дать концепцию. Детально Lakehouse можно будет разобрать позже.

---

# 6. MPP

Вводим ещё одну проблему:

> Что делать, если данных стало слишком много для одного сервера?

Ответ — распределённая обработка.

**MPP — Massively Parallel Processing.**

Вместо:

```text
         Query
           │
           ▼
       Server
           │
     10 млрд строк
```

получаем:

```text
              Query
                │
       ┌────────┼────────┐
       ▼        ▼        ▼
    Node 1    Node 2   Node 3
      │          │        │
   3 млрд     3 млрд   4 млрд
```

Каждый узел обрабатывает свою часть данных.

ClickHouse — хороший практический пример для знакомства с этой концепцией.

# 7. Batch vs Streaming

Теперь возвращаемся к ритейлу.

### Batch

```text
PostgreSQL
    │
    │ каждые 1 час
    ▼
 Airflow
    │
    ▼
ClickHouse
```

Плюсы:

* проще;
* дешевле;
* легче контролировать;
* хорошо подходит для большинства отчётов.

---

### Streaming

```text
POS
 │
 ▼
RabbitMQ
 │
 ▼
Consumer
 │
 ▼
ClickHouse
```

Данные движутся практически сразу.

Плюсы:

* низкая задержка;
* near-real-time аналитика;
* события доступны быстрее.

Минусы:

* сложнее;
* больше компонентов;
* сложнее обеспечить корректность;
* выше требования к monitoring/operations.

### Важный вопрос

> Нужно ли магазину знать продажи через 1 секунду?

Если:

**Нет** → возможно, достаточно batch.

Если:

**Да** → появляется streaming.

# 8. Эволюция архитектур

Собираем всё в одну картину:

```text
OLTP
 │
 │ аналитика становится сложнее
 ▼
OLAP
 │
 ▼
DWH
 │
 │ появляются новые типы данных
 ▼
Data Lake
 │
 │ нужно объединить подходы
 ▼
Lakehouse
 │
 │ растёт количество доменов/команд
 ▼
Data Mesh
```

И отдельно:

```text
Batch ───────────────► Streaming
```

Важно подчеркнуть:

> Это **не лестница, по которой все компании обязаны подняться до Data Mesh**.

Это эволюция проблем и способов их решения.
