# Занятие 8. Проектирование ETL/ELT-потока

Главная мысль занятия:

> ETL/ELT — это не просто перенос данных из одной базы в другую. Это управляемый процесс, который должен обеспечивать корректность, повторяемость, контролируемость и своевременность получения данных.

Как доставить данные из источника в спроектированную витрину так, чтобы процесс работал регулярно и надёжно?

```
PostgreSQL
    ↓
Извлечение данных
    ↓
Raw / staging
    ↓
Трансформации
    ↓
Проверки качества
    ↓
ClickHouse: sales_mart
    ↓
BI / аналитика
```

На этом занятии фокус — не на том, как нарисовать всю платформу, а на том, как спроектировать один конкретный поток данных.

# Что такое ETL и ELT

## ETL — Extract, Transform, Load

1. Extract — извлечь данные из источника.

2. Transform — преобразовать их.

3. Load — загрузить результат в целевую систему.

   Источник
   ↓
   Extract
   ↓
   Transform
   ↓
   Load
   ↓
   Целевая система

Пример:

* забрать заказы из PostgreSQL;

* очистить статусы, проверить суммы, привести типы;

* загрузить подготовленные данные в аналитическое хранилище.

В классическом ETL трансформация выполняется до загрузки в целевую систему.

## ELT — Extract, Load, Transform

1. Extract — извлечь данные.

2. Load — загрузить их в целевую систему или промежуточное хранилище.

3. Transform — преобразовать уже загруженные данные.

   Источник
   ↓
   Extract
   ↓
   Load
   ↓
   Raw / staging
   ↓
   Transform
   ↓
   Аналитическая витрина

Например:

* выгрузить исходные данные из PostgreSQL;

* сохранить их в S3;

* загрузить или обработать данные в ClickHouse;

* построить витрину с помощью SQL.

## ETL и ELT: сравнение

| Критерий                         | ETL                                           | ELT                                                          |
| -------------------------------- | --------------------------------------------- | ------------------------------------------------------------ |
| Когда выполняется трансформация  | До загрузки в целевую систему                 | После загрузки                                               |
| Где обычно обрабатываются данные | В отдельном processing-компоненте             | В целевом хранилище или аналитической платформе              |
| Преимущество                     | Можно очистить данные до попадания в target   | Можно сохранить исходные данные и гибко перестраивать модели |
| Ограничение                      | Processing-компонент может стать узким местом | Целевое хранилище должно справляться с трансформациями       |
| Пример                           | Python обрабатывает CSV и загружает результат | Данные загружаются, затем обрабатываются SQL-запросами       |

Важная оговорка: в реальных архитектурах граница не всегда строгая. Один pipeline может сочетать оба подхода.

ETL не устарел, а ELT не всегда лучше. Выбор зависит от объёма данных, возможностей целевого хранилища, требований к качеству, хранению исходных данных и стоимости обработки.

## Был задан вопрос `Что такое Processing-компонент?`

Processing-компонент — это то, что обрабатывает данные: берёт исходные данные, выполняет над ними нужные операции и выдаёт результат.

Представьте конвейер на заводе:

* Источник — привозит сырьё.

* Processing — очищает, сортирует, собирает и проверяет сырьё.

* Хранилище — хранит полученный результат.

* Потребитель — использует готовый продукт.

## Пример из ритейла

Допустим, кассы передают данные о продажах:

```
PostgreSQL
(исходные продажи)
      ↓
   Processing
      ↓
ClickHouse
(аналитическая витрина)
```

Processing-компонент может:

1. убрать дубликаты продаж;

2. привести даты и суммы к нужным форматам;

3. исключить или отдельно обработать отменённые чеки;

4. рассчитать выручку;

5. проверить корректность данных;

6. подготовить результат для загрузки в ClickHouse.

То есть он отвечает за преобразование данных из исходного вида в нужный вид.

## А что в нашей платформе выполняет Processing?

У нас есть PostgreSQL, S3, ClickHouse, Airflow и Python. Их роли разные.

| Компонент  | Роль                                                             |
| ---------- | ---------------------------------------------------------------- |
| PostgreSQL | Хранит исходные операционные данные                              |
| S3         | Хранит файлы и исходные наборы данных                            |
| Python     | Может выполнять обработку и преобразования                       |
| ClickHouse | Хранит и обрабатывает аналитические данные                       |
| Airflow    | Организует последовательность задач и запускает их по расписанию |

Обратите внимание: Processing — это роль в архитектуре, а не обязательно отдельный продукт.

Например, обработка может выполняться:

* Python-скриптом;

* SQL-запросом в ClickHouse;

* Spark или другим специализированным движком;

* несколькими инструментами вместе.

Airflow при этом обычно не обрабатывает сами данные. Он говорит: «Сначала запусти Python-скрипт, потом выполни SQL, затем проверь результат».

# Pipeline: из каких этапов он состоит

Data pipeline — последовательность операций, которая переносит или обрабатывает данные и управляет их прохождением через систему.

Рассмотрим пример загрузки продаж.

1. Extract

Получить новые или изменённые записи из PostgreSQL

2. Load to staging

Временно сохранить полученную порцию данных

3. Transform

Нормализовать типы, статусы, ключи и показатели

4. Validate

Проверить полноту и корректность результата

5. Publish

Обновить аналитическую витрину в ClickHouse

6. Monitor

Зафиксировать результат, длительность и ошибки

Это логическая схема: staging может быть таблицей в БД, файлами в S3 или промежуточным набором данных. Не каждому pipeline нужны отдельные физические компоненты для всех этапов.

## Что важно на каждом этапе

| Этап      | Основной вопрос                                         |
| --------- | ------------------------------------------------------- |
| Extract   | Какие данные забираем и как определяем изменения?       |
| Staging   | Где сохраняем полученную порцию до публикации?          |
| Transform | Какие бизнес-правила применяем?                         |
| Validate  | Как убеждаемся, что результат корректен?                |
| Publish   | Как обновляем витрину без потери и дублирования данных? |
| Monitor   | Как узнаём, что загрузка прошла успешно или сломалась?  |

# Способы загрузки данных

Один из главных архитектурных выборов — как получать данные из источника.

## Full load — полная загрузка

При каждом запуске читаем весь набор данных.

```
Источник: 1 000 000 строк
        ↓
Считываем все 1 000 000
        ↓
Перезаписываем целевой набор
```

Подходит, когда:

* таблица небольшая;

* данные обновляются редко;

* полная загрузка укладывается в допустимое окно;

* источник допускает повторное чтение.

Недостатки:

* повторная передача одних и тех же данных;

* нагрузка на источник;

* рост времени загрузки;

* сложность полной перезагрузки больших исторических таблиц.

Пример: справочник типов доставки из нескольких сотен строк.

## Incremental load — инкрементальная загрузка

Загружаем только новые или изменившиеся записи.

Например, в таблице есть `updated_at`.

SQL

```
SELECT *
FROM orders
WHERE updated_at > :last_successful_watermark;
```

Здесь `watermark` — сохранённая граница, до которой данные успешно обработаны.

Подходит, когда:

* таблица большая;

* изменения можно определить;

* источник поддерживает фильтрацию по времени или другому маркеру;

* полное чтение слишком дорого.

Но есть нюансы:

* записи могут поступать с опозданием;

* у нескольких записей может совпадать `updated_at`;

* `updated_at` может обновляться некорректно;

* физическое удаление строки обычно не обнаруживается таким запросом.

На практике часто используют небольшой временной overlap: повторно читают часть недавнего интервала и устраняют дубликаты по ключу и версии записи.

## Бал задан вопрос `Что такое watermark и где она хранится?`

Watermark — это отметка, до какого места данные уже успешно обработаны.

Представь, что в PostgreSQL миллион заказов. Каждый раз читать их все дорого, поэтому мы забираем только новые или изменившиеся записи.

Например, последний успешный запуск обработал данные до `10:00`.

```
PostgreSQL
    ↓
Забираем записи после 10:00
    ↓
Загружаем в ClickHouse
    ↓
Успех → сохраняем watermark = 10:15
```

При следующем запуске начинаем с сохранённой отметки.

## Как и где он хранится?

Watermark — это обычно обычное значение, например дата и время. Его нужно где-то сохранить, чтобы следующий запуск знал, с какого места продолжать.

Варианты:

* Таблица в PostgreSQL — например, `etl_state`.

* Таблица в ClickHouse — если это удобно для архитектуры.

* Метаданные или хранилище состояния pipeline — в зависимости от используемого инструмента.

Пример таблицы:

| pipeline_name  | last_successful_watermark |
| -------------- | ------------------------- |
| sales_pipeline | 2026-10-20 10:15:00       |

## CDC — Change Data Capture

CDC позволяет получать изменения в источнике: вставки, обновления и удаления.

```
PostgreSQL
    ↓
WAL / механизм CDC
    ↓
Change events
    ↓
Обработка изменений
    ↓
Целевая система
```

CDC полезен, когда:

* нужна низкая задержка;

* изменения происходят часто;

* нужно обнаруживать удаления;

* читать всю таблицу слишком дорого.

Но CDC добавляет сложности:

* обработка повторных событий;

* порядок изменений;

* управление позициями чтения;

* восстановление после сбоев;

* эволюция схемы;

* контроль отставания потока.

Выбор способа загрузки определяется требованиями и возможностями источника, а не популярностью технологии.

# Incremental load: еще немного про watermark

Предположим, последний успешный запуск обработал изменения до:

```
2026-10-15 06:00:00
```

Это значение — watermark.

Следующий запуск выбирает изменения после этой границы.

```
Последняя успешная граница
          ↓
       Extract
          ↓
       Transform
          ↓
       Validate
          ↓
        Load
          ↓
Обновить watermark только после успеха
```

Главное правило:

> Не продвигать watermark, пока данные не загружены и не подтверждены как успешно обработанные.

Иначе возможна ситуация:

1. Extract прочитал данные до 07:00.

2. Watermark обновили на 07:00.

3. Загрузка в ClickHouse упала.

4. Следующий запуск начнётся после 07:00.

5. Пропущенный интервал не будет обработан.

На практике полезно разделять:

* extraction watermark — до какой границы мы читаем;

* committed watermark — до какой границы данные надёжно опубликованы.


# Трансформации данных

Трансформация — это не только изменение формата. Она может включать техническую очистку и бизнес-логику.

### Технические трансформации

* привести типы данных;

* распарсить дату и время;

* нормализовать кодировку;

* переименовать поля;

* обработать `NULL`;

* устранить дубликаты.

### Бизнес-трансформации

* определить чистую выручку;

* исключить отменённые продажи из определённого показателя;

* привести статусы к единому справочнику;

* связать товар с категорией;

* рассчитать маржу по согласованному правилу.

Пример:

Исходная запись:

```
receipt_id = 1001
status = PAID
quantity = 2
unit_price = 100
discount = 20
```

Трансформация:

```
gross_amount = quantity × unit_price
net_amount = gross_amount - discount
```

Результат:

```
gross_amount = 200
net_amount = 180
```

Важно заранее определить семантику скидки: относится ли `discount` к единице товара или ко всей строке чека. Иначе формула может быть неправильной.

### Где выполнять трансформации?

| Место                | Когда подходит                                                                        |
| -------------------- | ------------------------------------------------------------------------------------- |
| Python               | Сложная логика, обработка файлов, вызовы API, нестандартные преобразования            |
| SQL в PostgreSQL     | Небольшие извлечения и операции, которые не создают чрезмерную нагрузку на production |
| SQL в ClickHouse     | Аналитические преобразования и построение витрин                                      |
| Processing-компонент | Специализированная обработка больших объёмов или сложных потоков                      |

Не следует переносить тяжёлые аналитические запросы на production-БД только потому, что там находятся исходные данные.

# Качество данных: что проверять

Pipeline, который завершился без технической ошибки, не обязательно произвёл корректные данные.

Например, запрос выполнился успешно, но загрузил только половину нужных строк.

Поэтому проверки качества — отдельная часть архитектуры.

## Основные категории проверок

| Проверка                                      | Пример                                                          |
| --------------------------------------------- | --------------------------------------------------------------- |
| Completeness — полнота                        | За ожидаемый интервал пришли данные                             |
| Uniqueness — уникальность                     | Нет повторов одного `receipt_id` и `line_id`                    |
| Validity — допустимость                       | `quantity > 0` или статус входит в справочник                   |
| Consistency — согласованность                 | Сумма строк чека совпадает с суммой чека с учётом бизнес-правил |
| Freshness — свежесть                          | Последние данные не старше установленного порога                |
| Referential integrity — ссылочная целостность | У каждого `product_id` есть соответствующий товар               |

Примеры SQL-проверок:

SQL

```
-- Проверка количества некорректных строк
SELECT COUNT(*)
FROM staging_sales
WHERE quantity <= 0;
```

SQL

```
-- Проверка дубликатов по бизнес-ключу
SELECT receipt_id, line_id, COUNT(*)
FROM staging_sales
GROUP BY receipt_id, line_id
HAVING COUNT(*) > 1;
```

Проверки должны иметь понятную реакцию на нарушение.

Например:

* остановить публикацию;

* отправить предупреждение;

* записать проблемные строки в quarantine;

* разрешить публикацию, но отметить витрину как неполную.

Не каждое нарушение обязано приводить к остановке pipeline — это определяется критичностью данных.

# Идемпотентность и повторный запуск

Представим:

1. Pipeline прочитал 10 000 записей.

2. Загрузил их в ClickHouse.

3. Упал до записи статуса успешного выполнения.

4. Airflow запустил задачу повторно.

5. Те же 10 000 записей загрузились ещё раз.

Что произошло?

Дублирование данных.

Поэтому нужно проектировать безопасный повторный запуск.

## Что такое идемпотентность

Идемпотентная операция при повторном выполнении приводит к тому же конечному состоянию, что и однократное выполнение.

Для pipeline это означает, что повторная обработка одной и той же порции данных не должна приводить к повторному учёту фактов.

Способы добиться этого:

* определить бизнес-ключ записи;

* хранить идентификатор загрузки или интервала;

* загружать данные во временный слой;

* дедуплицировать записи по ключу и версии;

* использовать корректную стратегию обновления или замены данных;

* публиковать результаты только после успешной проверки.

Важно: простое использование `INSERT` не делает загрузку идемпотентной. Также нельзя считать, что `UPSERT`, `MERGE` или механизм схлопывания строк автоматически решит все проблемы: нужно понимать гарантии выбранной СУБД и модель данных.

# Что делать при сбоях

Обсудим несколько типичных ситуаций.

### Сценарий A. Источник недоступен

Например, PostgreSQL не отвечает.

Варианты:

* ограниченное число повторных попыток;

* задержка между попытками;

* уведомление после исчерпания попыток;

* не продвигать watermark;

* сохранить состояние предыдущей успешной загрузки.

### Сценарий B. Загрузка в ClickHouse упала на середине

Нужно понять, какие данные уже опубликованы.

Возможные решения:

* загрузка сначала в staging, затем публикация;

* атомарная замена партиции, если это подходит модели и возможностям системы;

* повторная загрузка идемпотентной порции;

* контроль по `batch_id` и количеству записей.

### Сценарий C. Данные пришли, но проверка качества не прошла

Например, обнаружены неизвестные статусы.

Варианты:

* остановить публикацию;

* отправить ошибочные записи в quarantine;

* сохранить исходные данные для повторной обработки;

* уведомить ответственного.

### Сценарий D. Pipeline работает, но отстаёт

Например, загрузка запускается каждые 5 минут, но занимает 12 минут.

Это уже не просто ошибка отдельного запуска, а проблема производительности и расписания.

Нужно контролировать не только статус задачи, но и lag — отставание данных от источника.

# 11. Оркестрация: роль Airflow

Airflow — инструмент оркестрации workflow. Он управляет зависимостями задач, расписанием, повторами и состоянием выполнения.

Пример DAG:

```
extract_sales
      ↓
load_staging
      ↓
transform_sales
      ↓
validate_sales
      ↓
publish_sales_mart
      ↓
record_metrics
```

Каждый блок может быть отдельной задачей.

## Что Airflow делает

* запускает задачи по расписанию;

* обеспечивает порядок выполнения;

* управляет зависимостями;

* позволяет настроить retry;

* хранит историю запусков и статусы;

* помогает отслеживать ошибки.

## Чего Airflow сам по себе не делает

* не гарантирует корректность данных;

* не делает операции автоматически идемпотентными;

* не заменяет хранилище;

* не заменяет систему качества данных;

* не превращает любой скрипт в надёжный pipeline.

Например, `retry` полезен при временном отказе сети, но опасен, если повторный запуск без защиты повторно вставляет одни и те же продажи.

# Расписание и freshness — не одно и то же

Допустим, pipeline запускается каждые 10 минут.

Это не гарантирует, что данные обновляются каждые 10 минут.

Если одна загрузка занимает 8 минут, а затем возникает очередь, фактическая задержка будет больше.

Нужно различать:

* schedule interval — как часто запускается процесс;

* duration — сколько длится запуск;

* freshness — насколько свежи данные у потребителя;

* lag — насколько обработка отстаёт от источника.

Пример:

| Показатель                      | Значение |
| ------------------------------- | -------- |
| Частота запуска                 | 5 минут  |
| Длительность обработки          | 3 минуты |
| Задержка поступления в источник | 1 минута |
| Примерная freshness             | 4 минуты |

Это лишь упрощённый пример. Реальная freshness зависит от времени появления записи, задержек источника, ожидания запуска, обработки и публикации.

Архитектурное решение: если бизнес требует freshness не более 5 минут, одного расписания раз в 5 минут может быть недостаточно.
